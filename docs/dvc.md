# DVC — Data Version Control

## What DVC does in this project

DVC tracks two things:

1. **Data files** — `data/diabetes.csv` and `data/diabetes_synthetique.csv` are tracked by DVC (`.dvc` pointer files), not committed as raw bytes to Git. Git only stores the `.dvc` pointer (md5 hash + size).

2. **Pipeline stages** — `dvc.yaml` defines the 4 ML pipeline stages so that DVC can detect which outputs are stale and re-run only what changed.

## Current state

| Item | Status |
|---|---|
| DVC initialized | Yes (`.dvc/` folder present) |
| Remote storage configured | **No** — local cache only (`.dvc/cache/`) |
| Data files tracked | `data/diabetes.csv`, `data/diabetes_synthetique.csv` |
| Pipeline stages | 4 stages in `dvc.yaml` |
| Lock file | `dvc.lock` — records exact hashes of all stage inputs/outputs |

> **Important:** The `dvc.yaml` pipeline stages reference the **global** artifact paths (`artifacts/data/`, `artifacts/models/`, etc.), which correspond to the legacy direct execution mode. In the current `docker_per_user` mode, artifacts are written per-run to `artifacts/user_runs/<run_id>/`. The DVC pipeline is useful for local development and reproducibility, not for portal-triggered runs.

## File layout

```
.dvc/
├── cache/          ← local content-addressable cache of tracked files
├── config          ← remote storage config (empty — no remote set)
└── tmp/

data/
├── diabetes.csv                  ← actual file (DVC-managed)
├── diabetes.csv.dvc              ← Git-tracked pointer
├── diabetes_synthetique.csv
└── diabetes_synthetique.csv.dvc

dvc.yaml    ← pipeline stage definitions
dvc.lock    ← locked hashes of all deps + outs (commit this)
.dvcignore  ← patterns DVC should ignore (like .gitignore)
```

## Pipeline stages (`dvc.yaml`)

```
prepare  →  train  →  explain  →  audit
```

| Stage | Command | Key inputs | Key outputs |
|---|---|---|---|
| `prepare` | `python -m shared.run_phase2` | `data/diabetes.csv`, `config/project-config.json` | `artifacts/data/splits/`, `artifacts/data/metadata/` |
| `train` | `python -m server.run_training` | `artifacts/data/splits/`, `shared/modeling.py` | `artifacts/models/`, `artifacts/metrics/` |
| `explain` | `python -m explainability.shap_explainer` | `artifacts/models/`, `artifacts/metrics/` | `artifacts/xai/` |
| `audit` | `python -m audit.audit_pipeline` | `artifacts/xai/`, `artifacts/metrics/` | `artifacts/audit/` |

## Common commands

### Run the full pipeline (only stale stages re-run)

```bash
dvc repro
```

DVC checks `dvc.lock`. If a dep's hash changed, that stage and all downstream stages re-run. Otherwise skipped.

### Run a single stage

```bash
dvc repro prepare      # only Phase 2
dvc repro train        # Phase 3 (and prepare if stale)
```

### Check what would run without executing

```bash
dvc status
```

Shows which stages are stale (inputs changed since last `dvc repro`).

### Check data file status

```bash
dvc status data/diabetes.csv.dvc
```

### Pull data files from remote (when a remote is configured)

```bash
dvc pull
```

### Push data to remote

```bash
dvc push
```

## Setting up a remote (optional)

No remote is configured yet. To add one (e.g. local folder or S3):

```bash
# Local folder remote (simplest for sharing within a team on the same machine)
dvc remote add -d myremote /path/to/dvc-storage

# Google Drive remote
dvc remote add -d gdrive gdrive://<folder-id>

# S3 remote
dvc remote add -d s3remote s3://my-bucket/dvc-store
```

Then commit `.dvc/config` to Git and push data:

```bash
dvc push
git add .dvc/config && git commit -m "add dvc remote"
```

Teammates then run `dvc pull` to get the data files.

## Workflow for code changes

```
1. Edit code (e.g. shared/data_preparation.py)
2. dvc repro                   ← re-runs stale stages only
3. git add dvc.lock            ← lock file records new hashes
4. git commit -m "..."
5. dvc push                    ← push new artifact cache to remote (if configured)
```

## Workflow for new dataset version

```
1. Replace data/diabetes.csv with new version
2. dvc add data/diabetes.csv   ← updates diabetes.csv.dvc pointer + local cache
3. dvc repro                   ← re-runs all stages (diabetes.csv is a dep of prepare)
4. git add data/diabetes.csv.dvc dvc.lock
5. git commit -m "update dataset v2"
6. dvc push
```

---

## What NOT to do

- Do **not** `git add data/diabetes.csv` — the raw CSV is DVC-managed, not Git-managed. Git only tracks the `.dvc` pointer file.
- Do **not** delete `.dvc/cache/` manually — that is the local content store. Use `dvc gc` to clean unused cache entries.
- Do **not** edit `dvc.lock` by hand — it is auto-generated by `dvc repro`.

## Reproduce from scratch (clean environment)

```bash
# 1. Clone repo
git clone <repo-url>
cd ensaj

# 2. Pull data files (requires remote to be configured)
dvc pull

# 3. Run full pipeline
dvc repro

# 4. Start services
docker compose up -d
```

If no remote is configured, manually place `data/diabetes.csv` and run `dvc repro`.
